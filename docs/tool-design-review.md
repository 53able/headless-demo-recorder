# AIインターフェース設計／レビュー: headless-demo-recorder CLI（エージェント向けツール面）

## 1. 結論

- 判定: 改善が必要（主要な改善は実装済み。残りは未検証事項として §10 に記載）
- 主要判断: CLIを、リスク階層ごとに分けたコマンド（`doctor` / `check` / `capture` / `render` / `inspect` / `plan`）に分割した。録画を書き出し前に永続化し、失敗時は `retry` 区分付きの構造化JSONを返すようにした。
- 最大リスク: desktop の `capture` は実アプリを操作する。不可逆な操作の検出はキーワードによる推定でしかなく、モデル外のサンドボックスがない。

## 2. 対象と前提

| 項目 | 内容 |
|---|---|
| 作業モード | レビュー（既存コードと実行ログを確認したうえで改修） |
| 主要利用者 | CLIを呼ぶコーディングエージェント（Claude Code 等）。二次利用者は、成果物の動画を確認する人間 |
| 達成したい結果 | 依頼文から、意図した操作を正しく映したデモ動画（MP4/GIF）を、人がエディタを触らずに得る |
| AIの役割 | 実行（UIを操作して録画する）、共同編集（編集領域を生成する） |
| 外部システム | agent-browser 0.32.1、agent-desktop 1.0.2、OpenScreen 1.13 CLI、ffmpeg |
| 観測事実 | 改修前の `run` は録画・編集・書き出しを1コマンドで実行していた。書き出しに失敗すると一時ディレクトリごと録画が消え、再録画が必要だった。エラーは自由文字列だった。出力の上書きは無確認だった。動画の目視確認はエージェントが手作業で行っていた。破壊的な操作を止める仕組みはなかった |
| 仮定 | 呼び出し元のエージェントはJSONの `retry` と `hint` を読んで分岐する。利用者は録画対象のアプリについて、操作してよい範囲を事前に把握している |

## 3. リスク階層

| 操作 | 階層 | 可逆性 | 影響 | 必要な制御 |
|---|---|---|---|---|
| `doctor` / `check` / `plan` / `inspect` | R0 | 即時（外部状態を変えない） | なし | 自動 |
| `render`（プロジェクト再生成と出力ファイルの書き込み） | R1 | 即時（再実行で作り直せる） | 既存の出力の上書き | 自動。上書きは `--force` がある場合のみ |
| `capture` browser（新規の agent-browser セッション） | R2 | 条件付き（操作先のWebサービス次第） | 外部サイトでのフォーム送信など | `check` 通過を必須とする。推定上の破壊的ステップは拒否 |
| `capture` desktop（実アプリの操作） | R2 | 条件付き | アプリの状態変更。通知も録画に写り込む | `check` 通過を必須とする。警告を出す。推定上の破壊的ステップは拒否 |
| 削除・送信・購入などを含むステップ | R3 | 不可逆 | 実データの喪失や外部への送信 | 既定は実行禁止。利用者が承認した場合だけ `allowDestructive` で許可 |

## 4. 五段階の状態設計

| 段階 | 状態 | 利用者に見せる情報 | 可能な操作 | 失敗 | 復旧 |
|---|---|---|---|---|---|
| 構成 | 依存ツールと権限の確認 | `doctor` の項目別の ok / detail / fix | 再確認する。利用者へ権限付与を依頼する | ツールが未導入、権限が未付与 | 未付与なら止まり、付与は利用者に依頼する（ツール側では変更しない） |
| 入力 | シナリオの検証 | `check` の issue（パス・レベル・理由） | シナリオを修正して再検証する | スキーマ違反、破壊的と推定したステップ、`@eN` 参照 | `retry: after-fix`。何も起動していないことを `hint` で明示する |
| 計算 | 録画と操作の実行 | stderr の工程ログ | 待つ。中止する（SIGINTで録画を停止し、子プロセスも回収する） | 対象要素がない、タイムアウト | `TARGET_NOT_FOUND` を `retry: no` で返す。作業ディレクトリは保持する |
| 出力 | プロジェクトと動画 | 出力パス、ズーム数・注釈数、`inspectSheet` | `plan` で差分を見る。`events.json` や編集計画を直して `render` する | OpenScreen の拒否、空の出力 | 録画は保持される。`artifacts.retryWith` で書き出しだけを再実行できる |
| 行動 | 成果物の採用 | 目視確認用のコンタクトシート | 採用、再編集、再録画（`--force`） | 誤ったズームや個人情報の写り込み | `render` で再編集する（数秒で済み、再録画は不要） |

## 5. 主要な設計判断

### D-01: 録画を書き出し前に永続化し、工程を分割する

- 対象状態: 出力・復旧
- 変更前または現状: `run` が一時ディレクトリで録画し、`finally` で削除していた。書き出しに失敗すると録画が消えた。
- 提案: `capture` は `<out>.project/` に `capture.mp4`、`capture.json`、`events.json` を保存する。`render` は保存済みのプロジェクトから何度でも再生成できる。`run` で書き出しが失敗した場合は `retryWith` を返す。
- 根拠: 確率的な失敗からの回復。成功済みの工程を保存する（原則6）。
- トレードオフ: プロジェクトディレクトリが出力の横に残り、ディスクを使う。
- 受入条件: 保存済みプロジェクトに対する `render` が、再録画なしで成功する。
- 未検証事項: 長時間の録画でのディスク使用量。

### D-02: 結果を1つのJSONにまとめ、`retry` を3値で返す

- 対象状態: 全段階の失敗
- 変更前または現状: `{ok:false, error:"<文字列>"}` だけを返していた。エージェントは再試行してよいかを判断できなかった。
- 提案: `stage`、`code`、`retry`（safe / after-fix / no）、`hint`、`artifacts`、成功時の `next` を返す。録画中に起きた失敗は必ず `retry: no` とする（実アプリで操作が途中まで進んでいるため）。
- 根拠: 盲目的な再試行による二重の副作用を防ぐ（チェックリスト6「重複実行と再開時の二重副作用を防ぐ」）。
- トレードオフ: 呼び出し側がコード体系に依存するようになる。
- 受入条件: 検証失敗、出力の衝突、録画の衝突、対象要素なし、プロジェクトなし、の各ケースで、異なる `code` と適切な `retry` が返る。
- 未検証事項: エージェントが実際に `retry` に従うか（運用での観測が必要）。

### D-03: 起動前の静的検証と、破壊的操作のガード

- 対象状態: 入力
- 変更前または現状: 検証は名前と出力パスの存在確認だけだった。削除や送信のステップもそのまま実行していた。
- 提案: `check` を独立したコマンドにし、`run` と `capture` でも必ず通す。破壊的と推定したステップは拒否する。例外の許可は、ステップ単位（無害だと確認済み）とシナリオ単位（利用者が承認済み）の2段階にする。出力が既にある場合は、録画を始める前に止める。
- 根拠: 権限は最小・具体的にする（原則9）。高リスクの作業では先に止める（原則10）。
- トレードオフ: キーワード推定のため誤検知が出る（実測で、計算機の「すべて消去」が拒否された）。逆に見逃しもあり得る。
- 受入条件: `text=Delete` を含むシナリオが、何も起動せずに `INVALID_SCENARIO` で止まる。ステップ単位の許可は、そのステップにしか効かない。
- 未検証事項: 見逃し率。キーワードに当たらない破壊的なボタン（アイコンだけのゴミ箱など）は検出できない。

### D-04: 目視確認用の証拠を自動で生成する

- 対象状態: 出力
- 変更前または現状: 書き出しが成功すれば完了とみなしていた。エージェントが手作業で ffmpeg を呼んで確認していた。
- 提案: `inspect` が、各アクションの約350ms後のフレームを並べた `inspect-sheet.png` を作る。`run` の結果で、その確認を `next` として指示する。
- 根拠: 流暢に見えることや終了コード0を、正しさの証拠にしない（原則7・8）。
- トレードオフ: ツール自身は正否を判定しない。判定はエージェントまたは人間に委ねる。
- 受入条件: `run` の成功時に `inspectSheet` が存在し、タイル数がアクション数と一致する。
- 未検証事項: 速度変更（speed-up）がある場合、フレーム時刻は比率による近似になる。

### D-05: 読み取り専用の事前診断

- 対象状態: 構成
- 変更前または現状: 権限が足りないと、録画を始めてから失敗していた。`openscreen --version` を実行すると GUI が起動していた（実際に発生した）。
- 提案: `doctor` が、ツール、バージョン、Accessibility と Screen Recording の権限、OpenScreen CLI の有無を確認する。GUI を起動しない `openscreen help` だけを使う。
- 根拠: 能力と制約を、必要な時点で示す（原則2）。
- トレードオフ: 実行時間が数秒増える。
- 受入条件: `doctor` が GUI を開かずに全項目を返す。
- 未検証事項: 権限が未付与の環境での表示（この環境では付与済みのため未確認）。

## 6. 権限・承認・共有制御

- 計画を見せる条件: R2 の `capture` の前には `check` が必ず走る。シナリオ自体が、実行前に読める計画になっている。
- 直前承認が必要な操作: 破壊的と推定したステップ（R3）。CLI は対話的な承認を持たないため、既定で拒否する。承認は、利用者の同意を得たエージェントがシナリオに明示する。
- 許可の範囲と期限: `allowDestructive` は、そのシナリオファイル（またはそのステップ）に限って有効。期限はない。
- 拒否後の挙動: 何も起動しない（`hint: nothing was launched`）。別の経路から自動で実行し直すことはない。
- 一時停止・再開・中止: 中止は SIGINT と、録画子プロセスの段階的な終了（stop → SIGTERM → SIGKILL）。一時停止と再開は未実装。
- 取消・補償操作: 録画中のアプリ操作は取り消せない。失敗時は `retry: no` で停止し、アプリの状態確認を求める。ファイル出力は `--force` がない限り上書きしない。
- モデル外の安全境界: なし（後回し）。CLI の `--allow-origin`（browser の通信先をホスト単位で制限する）と `--allow-app`（desktop の入力先を制限する。システム系アプリ・ブラウザは常に拒否）は任意指定の防御で、指定するかどうかは呼び出し元のエージェントに委ねられる。録画予算、許可リストの強制、録画前の人間による承認は実装していない（以前の設計は git 履歴 a66b495 を参照）。
- 監査記録: `events.json`（実行したアクション、対象、時刻）と `capture.json` が残る。入力値（`fill` の value）はイベントに保存しないが、録画の映像には映る。

## 7. 信頼・倫理・アクセシビリティ

- 根拠と適用範囲: ズームの位置はアクション対象要素の矩形に基づく。動画上の位置は `inspect` で照合できる。
- 不確実性の伝え方: browser の時刻補正値（scale）を stderr に出す。速度変更がある場合、`inspect` の結果に「近似」と注記する。
- データ利用と記憶: ツールは記憶を持たない。録画、プロジェクト、OpenScreen の録画フォルダの原本がローカルに残る。削除は利用者が行う。
- 異議申立てと救済: 対象外（利用者が自分の画面を録る道具であるため）。
- 影響を受ける人: 録画に映る第三者（通知、共有画面、メール本文）。対策は `redact` と desktop 警告だけで、自動検出はない。
- キーボードと支援技術: CLI は全操作をキーボードで完結できる。成果物の動画については、字幕は注釈として焼き込むだけで、音声説明はない。
- 代替操作: 色に依存する情報はない。成果物は動画だけで、テキストの代替（文字起こし）は未提供。

## 9. 受入条件

| ID | 条件 | 検証方法 | 責任者 | 停止条件 |
|---|---|---|---|---|
| AC-01 | すべてのコマンドが stdout に JSON を1つだけ出す | 各コマンドを実行し、出力を JSON としてパースする | 実装者 | パースに失敗したら修正するまでリリースしない |
| AC-02 | `capture` 以前の失敗では何も起動しない | `check` の失敗と `OUTPUT_EXISTS` の時点で、プロセスとウィンドウが起動していないことを確認 | 実装者 | アプリやブラウザが起動したら停止する |
| AC-03 | 録画中の失敗は必ず `retry: no` で返り、録画プロセスが残らない | 失敗シナリオの実行と `pgrep` | 実装者 | 残存プロセスがあれば停止する |
| AC-04 | 保存済みプロジェクトからの `render` が再録画なしで成功する | `render <project> --edit` | 実装者 | 録画ファイルが消えていたら停止する |
| AC-05 | 破壊的と推定したステップは明示の許可なしに実行されない | `validate.test.ts` | 実装者 | テストが失敗したらリリースしない |

## 10. 未検証事項と次の一歩

- 未検証: 書き出し失敗時の `retryWith` の実地確認。権限が未付与の環境での `doctor` 表示。破壊的ステップの見逃し率。呼び出し元のエージェントが `retry` に従うかどうか。
- 残存リスク: モデル外の安全境界がない。desktop の録画は実アプリと実画面を使う。アイコンだけの破壊的ボタンはガードを通過する。録画に映る第三者の情報は自動では保護されない。
- 次に行う最小検証: OpenScreen の書き出しを失敗させる注入テスト（読み取り専用の出力先を指定する）で AC-04 の経路を確認する。続いて、専用ユーザーまたは VM 上で desktop 録画を行う構成を試す。
- Codex のサンドボックス（2026-11-02 実測、`codex sandbox -c sandbox_mode=workspace-write`）: `check`・`plan`・`inspect`・file ソースの capture（ffmpeg）は動く。`openscreen` を起動するもの（`doctor` の `openscreen help`、`render` の `openscreen info` / `export`）は、Electron アプリがウィンドウサーバーへの登録を拒否されて SIGABRT で終了し、クラッシュレポートとダイアログが出る。`doctor` は `agent-desktop permissions` も `Operation not permitted` で失敗し、エラー応答の形式番号（`2.5`）をバージョンと誤読する。`render` の失敗は空のメッセージの `PROJECT_INVALID` になり、原因が分からない。
- 未検証（任意指定の防御）: `--allowed-domains` のポート付きパターンの効き方。許可したホストの別ポートへの、ページの JS による通信の遮断。`lsappinfo` と拒否リストの前方一致による bundle ID の照合。専用ユーザーまたは VM での desktop 自動化は未着手（F-1）。
